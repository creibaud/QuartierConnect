This documentation is aimed at developers and integrators who contribute to **QuartierConnect** or consume its API. It covers the platform architecture, its three databases, the query DSL, the JavaFX desktop plugin system, offline synchronisation, layered security and production deployment.

QuartierConnect is a **multi-component** platform: 4 active applications and 3 databases orchestrated through Docker Compose, plus a single external HTTP integration (Nominatim / OpenStreetMap) used for address geocoding.

## Interactive API reference (Scalar)

The complete, interactive REST API reference is generated by **Scalar** and served directly by the NestJS API. It is the source of truth for endpoints, DTOs, status codes and response schemas.

- **Locally**: `api:5000/docs`, exposed by Caddy under `/api/docs`.
- **In production**: reachable through Caddy under `/docs` (internal proxy to the API).

> Always use Scalar rather than this documentation for the exact signature of an endpoint: it is generated from the code and stays in sync with the NestJS implementation.

Every incoming call goes through Caddy, the single HTTP/HTTPS entry point. The `/api` prefix is stripped before proxying to the API, which then applies, in order, the Helmet headers, the `ThrottlerGuard`, the `JwtAuthGuard` (checking for a revoked `jti`), and finally the `ValidationPipe` before reaching the controller.

## Monorepo layout

The repository gathers the web surfaces, the API, the native desktop client and the DSL. The main landmarks:

| Location | Role |
|----------|------|
| `api/src` | NestJS API — REST + WebSocket + DSL gateway |
| `api/src/geocoding/geocoding.service.ts` | Only outbound integration (Nominatim) |
| `api/src/common/schemas/geo-point.schema.ts` | Reusable GeoJSON Point subdocument |
| `packages/ui/src/components/map.tsx` | Shared `<Map>` component (react-leaflet) |
| `packages/shared/src/lib/geo.ts` | Geo helpers (`centroidOf`, `pointToLatLng`, `latLngToPoint`) |

At runtime, the stack runs on **9 containers**: `caddy` (HTTPS reverse proxy + Let's Encrypt), `client` (resident React SPA, `:3000`), `admin` (back-office React SPA, `:3001`), `docs-user` (Fumadocs user help, `:3002`), `docs-dev` (Fumadocs developer documentation, `:3003`), `api` (NestJS `:5000`, embedding the Python PLY DSL gateway), `mongo` (`:27017`), `postgres` (`:5432`) and `neo4j` (`:7474`/`:7687`).

Caddy routing is as follows:

```
/          → client:3000
/admin     → admin:3001
/aide      → docs-user:3002
/dev       → docs-dev:3003
/api       → api:5000
/api/docs  → api:5000/docs (Scalar)
```

### NestJS modules

`AppModule` composes the business modules around `DrizzleModule` (PostgreSQL ORM): `AuthModule`, `NeighborhoodsModule`, `ServicesModule`, `IncidentsModule`, `EventsModule`, `PointsModule`, `UsersModule`, `SocialModule` (Neo4j driver), `ContractsModule`, `BookingsModule`, `MessagingModule`, `VotesModule`, `DocumentsModule`, `DslModule`, `CommunityVotesModule` and `GeocodingModule`.

### Data split

Choosing three engines answers distinct constraints:

- **PostgreSQL** — strictly ACID data: `users` (auth, roles, tokens), `incidents` (state machine), `points_balances` and `points_transactions`.
- **MongoDB** — flexible documents: `neighborhoods` (GeoJSON `2dsphere`), `services`, `events`, `contracts`, `messages`/`conversations`, `votes`, `communityVotes`, `documents` (GridFS) and `ssoTokens` (5 min TTL index).
- **Neo4j** — social graph: `User`, `Neighborhood`, `Service`, `Event` nodes linked by `LIVES_IN`, `LOCATED_IN`, `HELD_IN`, `INTERESTED_IN`, `USED`, feeding the Cypher recommendations.

Synchronisation to Neo4j is **fire-and-forget**: a graph outage never blocks the API, and `withRetry` retries up to 3 times with exponential backoff (100/200/400 ms) on a recoverable error.
