## À quoi sert le DSL

Le DSL de QuartierConnect est un **micro-langage de requête** qui permet aux modérateurs et aux administrateurs d'interroger les collections de l'application sans écrire de code. Il est exposé via `POST /dsl/query` et consommé depuis le panneau d'administration React. Un **modérateur** n'accède qu'aux données de son propre quartier ; seul l'**administrateur** interroge l'ensemble des données.

Le choix d'un DSL plutôt que de MongoDB brut répond à trois objectifs :

- **Sécurité** : les requêtes MongoDB brutes peuvent exprimer des injections complexes.
- **Simplicité** : une syntaxe quasi en langage naturel, utilisable sans formation MongoDB.
- **Contrôle** : une liste blanche de collections et aucune opération destructive.

Techniquement, le composant `dsl/` est écrit en **Python** avec **PLY** (lexer + parser LALR(1)), et invoqué depuis NestJS via le pont **pythonia**.

## Syntaxe

### Verbes et mots réservés

Deux verbes seulement : `FIND` (renvoie des documents) et `COUNT` (renvoie un entier). Les mots réservés — `FIND`, `WHERE`, `AND`, `OR`, `LIMIT`, `COUNT`, `IN`, `LIKE` — sont **insensibles à la casse** : `find`, `FIND` et `Find` sont équivalents.

### Grammaire

```
query : FIND IDENTIFIER
      | FIND IDENTIFIER WHERE conditions
      | FIND IDENTIFIER LIMIT NUMBER
      | FIND IDENTIFIER WHERE conditions LIMIT NUMBER
      | COUNT IDENTIFIER
      | COUNT IDENTIFIER WHERE conditions

conditions : condition
           | conditions AND condition   → merge des filtres
           | conditions OR condition    → {'$or': [left, right]}

condition : IDENTIFIER EQ  value        → {field: value}
          | IDENTIFIER NEQ value        → {field: {'$ne': value}}
          | IDENTIFIER GT  value        → {field: {'$gt': value}}
          | IDENTIFIER GTE value        → {field: {'$gte': value}}
          | IDENTIFIER LT  value        → {field: {'$lt': value}}
          | IDENTIFIER LTE value        → {field: {'$lte': value}}
          | IDENTIFIER LIKE value       → {field: {'$regex': re.escape(v), '$options': 'i'}}

value : STRING | NUMBER | IDENTIFIER
```

Les opérateurs de comparaison disponibles sont donc `=`, `!=`, `>`, `>=`, `<`, `<=` et `LIKE`. `LIKE` est une recherche de **sous-chaîne littérale** insensible à la casse : la valeur est échappée par `re.escape` avant d'être passée en `$regex`, si bien que les métacaractères (`.`, `*`, `[`, `(`, …) sont traités **littéralement** et non comme un motif — ce n'est donc pas une expression régulière active (protection anti-ReDoS). Les valeurs sont des chaînes (`'open'`, `"Paris"`), des nombres (`42`, `3.14`) ou des identifiants. Les espaces, tabulations et retours à la ligne sont ignorés.

### Exemples

```
FIND incidents
→ db.incidents.find({})

FIND incidents LIMIT 5
→ db.incidents.find({}).limit(5)

COUNT incidents
→ db.incidents.countDocuments({})

FIND incidents WHERE status = 'open'
→ db.incidents.find({status: 'open'})

FIND services WHERE type = 'free' AND category = 'gardening'
→ db.services.find({type:'free', category:'gardening'})

FIND services WHERE type = 'free' OR type = 'exchange'
→ db.services.find({$or:[{type:'free'},{type:'exchange'}]})

FIND services WHERE title LIKE 'garden'
→ db.services.find({title:{$regex:'garden',$options:'i'}})   # sous-chaîne littérale

FIND services WHERE title LIKE 'a.b'
→ db.services.find({title:{$regex:'a\.b',$options:'i'}})      # métacaractères échappés

FIND events WHERE maxAttendees >= 50 LIMIT 10
→ db.events.find({maxAttendees:{$gte:50}}).limit(10)
```

## Comment une requête est exécutée

Le pipeline est linéaire, du texte au résultat JSON :

1. **Requête HTTP** — `DslController` reçoit le `POST /dsl/query`, protégé par `JwtAuthGuard` + `RolesGuard` avec `@Roles('moderator', 'admin')`. Le DTO `DslQueryDto` borne la **longueur de la requête à 500 caractères** (`@MaxLength(500)`). Le `req.user` (rôle + `neighborhoodId`) est transmis au service, qui s'en sert pour le scoping par quartier.
2. **Lexer** (`dsl/lexer.py`) — découpe le texte en tokens (`FIND`, `IDENTIFIER`, `WHERE`, `STRING`…).
3. **Parser** (`dsl/parser.py`) — grammaire **LALR(1)** produisant un AST sous forme de `dict` Python (`type`, `collection`, `filter`, `limit`).
4. **Compilateur** (`dsl/compiler.py`) — valide la collection contre une **liste blanche** et renvoie l'AST.
5. **Sérialisation de l'AST** (`dsl/main.py`) — `main.py` renvoie l'AST compilé **en JSON** via pythonia ; le code Python n'accède plus à aucune base (il n'y a plus de Motor).
6. **Exécution** (NestJS `DslService`) — c'est le service Node qui exécute la requête : **Mongoose** pour `neighborhoods`, `services` et `events`, **Drizzle/PostgreSQL** pour `incidents` et `users`. Le service applique ici le **scoping par quartier** (pour tout demandeur non-admin) et **plafonne à 100 résultats** (`MAX_DSL_RESULTS`).
7. **Retour** — le résultat remonte à NestJS : un tableau de documents pour un `find`, `{ count: N }` pour un `count`.

La frontière est nette : `lexer.py`, `parser.py` et `compiler.py` ne font que produire un `dict` Python sérialisé en JSON (voir `main.py`, `execute` renvoie `json.dumps(result)`). Le `DslService` désérialise ce JSON en `CompiledQuery`, choisit le moteur d'après la collection, ajoute le filtre `neighborhoodId` pour tout demandeur non-admin, puis borne la sortie via `clampLimit` (`Math.min(limit ?? 100, 100)`).

### AST généré

```python
# "FIND incidents WHERE status = 'open' LIMIT 10"
{
    'type': 'find',
    'collection': 'incidents',
    'filter': {'status': 'open'},
    'limit': 10,
}
```

### Compilation côté Python

Le Python ne fait plus que **compiler** : `main.py` renvoie l'AST sérialisé, sans jamais toucher à une base de données.

```python
def execute(query_string: str) -> str:
    # Compile et renvoie l'AST en JSON — aucune exécution MongoDB ici.
    result = compile_query(query_string)
    return json.dumps(result)
```

### Exécution et scoping côté NestJS

`DslService` désérialise l'AST puis exécute la requête selon la collection, en appliquant le **plafond de 100 résultats** et le **scoping par quartier** pour tout demandeur non-admin.

```ts
// dsl.service.ts
const MAX_DSL_RESULTS = 100; // plafond réel, appliqué par clampLimit

// neighborhoods        → Mongoose (public, jamais scopé)
// services / events    → Mongoose + filtre { neighborhoodId } si non-admin
// incidents / users    → Drizzle/PostgreSQL + filtre neighborhoodId si non-admin
// Un non-admin sans neighborhoodId reçoit un résultat vide (sauf neighborhoods).
```

> Le point d'application du scoping est ici, dans NestJS — pas dans le Python. Un modérateur ne peut donc pas contourner le cloisonnement par quartier via le DSL.

## Sécurité et garde-fous

| Vecteur | Mitigation |
|---------|-----------|
| Collections arbitraires | Liste blanche stricte : `incidents`, `neighborhoods`, `services`, `events`, `users` |
| Opérations destructives | `FIND` et `COUNT` uniquement — aucun `DELETE`/`UPDATE`/`INSERT` |
| Injections (Mongo / SQL) | Les valeurs passent par le moteur (Mongoose ou requêtes Drizzle paramétrées) — aucune concaténation |
| ReDoS via `LIKE` | La valeur est échappée par `re.escape` : `LIKE` est une sous-chaîne littérale, jamais un motif regex actif |
| Accès non autorisé | Route protégée par `@Roles('moderator', 'admin')` |
| Fuite inter-quartiers | Un modérateur est scopé à son `neighborhoodId` (services, events, incidents, users) ; seul l'admin est global, `neighborhoods` reste public |
| Ressources excessives | 100 résultats maximum par requête (`MAX_DSL_RESULTS`, appliqué côté NestJS) |

Ces garde-fous forment une chaîne : chaque étape peut rejeter la requête, et seules celles qui franchissent tous les contrôles atteignent une lecture paramétrée. Le rôle est vérifié par le `RolesGuard` (403), le verbe et la collection par la grammaire puis le compilateur (400), tandis que le scoping, l'échappement de `LIKE` et le plafond sont des transformations appliquées côté NestJS avant l'accès au moteur.

Deux points méritent d'être soulignés. D'abord, la **lecture seule** n'est pas une règle ajoutée mais une propriété de la grammaire : le lexer ne connaît que `FIND`, `COUNT`, `WHERE`, `AND`, `OR`, `LIMIT` et `LIKE` ; un mot comme `DELETE` produit donc une `SyntaxError` avant tout accès. Ensuite, les collections adossées à PostgreSQL (`incidents`, `users`) n'acceptent qu'une **égalité simple** sur un champ contrôlé (`status`, `role`) via `extractEqualityFilter` — tout filtre plus riche est rejeté par un `BadRequestException`, ce qui interdit d'injecter des opérateurs Mongo (`$gt`, `$regex`, `$or`) dans une requête SQL.

## Erreurs courantes

| Erreur | Cause | Message |
|--------|-------|---------|
| `SyntaxError` | Token illégal (`FIND !@#`) | `Illegal character '!' at position 5` |
| `SyntaxError` | Grammaire invalide (`FIND WHERE incidents`) | `Syntax error at 'WHERE'` |
| `SyntaxError` | Fin prématurée (`FIND incidents WHERE`) | `Unexpected end of input` |
| `ValueError` | Collection non autorisée (`FIND passwords`) | `Unknown collection 'passwords'. Allowed: ...` |

> Une collection hors liste blanche est rejetée par le compilateur avant tout accès à la base : la requête n'atteint jamais MongoDB.
