L'API REST de QuartierConnect est construite avec NestJS et expose 86 routes réparties en 16 modules fonctionnels. La version courante est `3.0`. Ce guide décrit les mécanismes transverses — authentification, pagination et rôles — communs à l'ensemble des endpoints. Pour le détail route par route (schémas de requête, de réponse et essais en direct), consultez la référence interactive Scalar.

## Serveurs

Deux serveurs sont déclarés dans la spécification OpenAPI :

- `http://localhost:5000` — accès direct au service.
- `http://localhost/api` — via le reverse proxy Caddy.

## Authentification

Toutes les routes protégées reposent sur un **JWT Bearer** signé en **HS256**, d'une durée de vie de **15 minutes**. Le jeton se transmet dans l'en-tête HTTP :

```
Authorization: Bearer <accessToken>
```

### Cycle d'authentification

1. **Création de compte** via `POST /auth/register` : le secret **TOTP** est renvoyé dans le champ `otpauthUrl`.
2. **Connexion** via `POST /auth/login` avec email + mot de passe + code TOTP à 6 chiffres.
3. Le `accessToken` renvoyé est utilisé dans l'en-tête `Authorization`.

Le jeton d'accès (15 min) est accompagné d'un **refresh token** de 7 jours, déposé dans un cookie `qc_rt` **httpOnly** (`SameSite=strict`, `Secure` en production). Le renouvellement se fait via `POST /auth/refresh`, avec **rotation** du refresh token : l'ancien est invalidé à chaque échange. À la déconnexion (`POST /auth/logout`), le hash du refresh token est effacé en base et le jeton d'accès courant est révoqué via une liste de JTI bloqués.

La méthode `AuthService.login` enchaîne **trois vérifications** côté serveur avant d'émettre la paire de jetons : l'existence du compte (et l'absence de bannissement), le mot de passe (haché en **Argon2**), puis le code **TOTP** protégé contre le rejeu. Le refresh token n'est jamais stocké en clair — seul son hash Argon2 est conservé sur la ligne utilisateur PostgreSQL (`refreshTokenHash`), et l'`accessToken` embarque un `jti` unique pour la révocation.

La garde anti-rejeu vit dans `TotpService` : chaque couple `secret:code` accepté est mémorisé pendant 90 secondes, si bien qu'un code intercepté ne peut être rejoué même s'il reste dans sa fenêtre de validité de 30 s. La vérification `speakeasy` utilise `window: 1` (tolérance d'un pas de temps pour la dérive d'horloge).

> Un mode SSO à jeton unique (`POST /auth/sso/generate` puis `POST /auth/sso/exchange`, TTL 5 min) permet d'ouvrir une session sur le client lourd JavaFX sans re-saisir les identifiants. Le paramètre optionnel `state` (protection CSRF de type PKCE) est vérifié lors de l'échange.

### Rotation du refresh token

`TokenService.rotateRefreshToken` opère sous **transaction PostgreSQL** avec un verrou de ligne `SELECT ... FOR UPDATE`. Ce verrou protège contre une course **TOCTOU** (*time-of-check to time-of-use*) : si deux requêtes `POST /auth/refresh` arrivent avec le même token, une seule franchit la vérification. La première invalide le hash (`refreshTokenHash = null`) dans la même transaction ; la seconde, débloquée après le `COMMIT`, ne trouve plus de hash et échoue en `401 TOKEN_REVOKED`. Un compte redevenu `banned` entre-temps est également rejeté (`ACCOUNT_BANNED`). Une nouvelle paire n'est signée qu'après la validation, et son hash est réenregistré hors transaction.

<Mermaid
  chart={`sequenceDiagram
  participant C as Client
  participant Ctrl as Controller
  participant Tok as TokenService
  participant DB as PostgreSQL
  C->>Ctrl: POST /auth/refresh (cookie qc_rt ou corps)
  Ctrl->>Tok: rotateRefreshToken(token)
  Tok->>Tok: jwtService.verify — sinon 401 TOKEN_INVALID
  Tok->>DB: BEGIN puis SELECT ... FOR UPDATE
  Note over Tok,DB: Verrou de ligne — anti-TOCTOU : une seule rotation concurrente passe
  Tok->>Tok: argon2.verify(hash stocké, token)
  Note over Tok: hash absent ou invalide — 401 TOKEN_REVOKED
  Tok->>DB: UPDATE refreshTokenHash = null (invalide le précédent)
  Tok->>DB: COMMIT
  Tok->>DB: enregistre le hash du nouveau refresh token
  Tok-->>Ctrl: nouvelle paire — access 15 min + refresh 7 j
  Ctrl-->>C: 200 + nouveau cookie qc_rt`}
/>

Le token de renouvellement est lu en priorité dans le cookie `qc_rt`, avec repli sur le corps de requête (`refreshToken`) pour la compatibilité du client bureautique JavaFX qui ne gère pas les cookies.

### MFA TOTP sur les actions sensibles

Un code **TOTP** (30 s de validité, 6 chiffres) est exigé, en plus de la session, pour les opérations sensibles suivantes :

| Action | Route |
|--------|-------|
| Connexion | `POST /auth/login` |
| Signature d'un contrat | `POST /contracts/:id/sign` |
| Changement de mot de passe | `PATCH /users/me/password` |
| Changement d'email | `PATCH /users/me/email` |
| Changement de téléphone | `PATCH /users/me/phone` |
| Suppression du compte | `DELETE /users/me` |

Deux limitations de débit protègent le flux : la connexion est plafonnée à **5 tentatives par 15 minutes**, le renouvellement de jeton à **10 par minute**.

## Pagination et listes

Les endpoints de liste partagent un **contrat commun** implémenté dans `api/src/common/pagination.ts` (`parsePagination`, `resolveSort`, `escapeLike` / `escapeRegex`, `setPageHeaders`). Recherche, tri et filtres sont appliqués **côté serveur** — ils portent donc sur l'ensemble des données correspondantes, pas seulement sur la page déjà chargée. Chaque endpoint accepte les paramètres de requête suivants :

| Paramètre | Rôle | Défaut |
|-----------|------|--------|
| `page` | Numéro de page (à partir de `1`) | `1` |
| `limit` | Taille de page — bornée à l'intervalle `1`–`100` par `parsePagination` | `20` |
| `search` | Sous-chaîne insensible à la casse (champs selon l'endpoint) | — |
| `sort` | Champ de tri (liste blanche par endpoint) | `createdAt` |
| `order` | Sens du tri : `asc` ou `desc` | `desc` |

```
GET /incidents?page=2&limit=20&search=poutre&sort=createdAt&order=desc
```

### Filtres par endpoint

À ces paramètres communs s'ajoutent des filtres propres à chaque liste, ainsi que les champs sur lesquels porte `search` et la liste blanche de `sort` :

| Endpoint | Filtres additionnels | `search` porte sur | Champs `sort` autorisés |
|----------|----------------------|--------------------|-------------------------|
| `GET /incidents` | `status` (`open`/`in_progress`/`resolved`), `category` (`neighborhood`/`reporting`/`bug`) | titre + description | `createdAt`, `updatedAt`, `status` |
| `GET /services` | `category`, `type` (`free`/`paid`/`exchange`), `direction` (`offer`/`request`) | titre + description | `createdAt`, `title` |
| `GET /events` | `category`, `date` (`YYYY-MM-DD`, jour entier) | titre | `createdAt`, `date`, `title` |
| `GET /neighborhoods` | — | nom + ville | `createdAt`, `name` |
| `GET /community-votes` | `status` (`open`/`closed`, selon `endsAt`) | titre | `createdAt`, `endsAt` |
| `GET /users` (admin) | `role` (`resident`/`moderator`/`admin`/`banned`, valeur inconnue ignorée) | email | `createdAt`, `email`, `role` |

### Corps de réponse et métadonnées

Le **corps de la réponse reste un tableau nu** d'entités — inchangé pour les consommateurs existants, notamment le pull incrémental du client bureautique (`GET /incidents?since=…`). Les métadonnées de pagination voyagent dans deux **en-têtes de réponse** posés par `setPageHeaders` :

- `X-Total-Count` — nombre total d'éléments correspondant au filtre, toutes pages confondues.
- `X-Total-Pages` — nombre total de pages (`ceil(total / limit)`, au minimum `1`).

Ces deux en-têtes sont **exposés via CORS** (`exposedHeaders` dans `api/src/main.ts`) afin d'être lisibles depuis le navigateur. Côté web, le helper `apiGetPage` (`web-apps/packages/shared/src/lib/api.ts`) les lit et renvoie `{ data, total, totalPages }` ; en leur absence il retombe sur `data.length` et `1`.

```http
GET /incidents?page=2&limit=20&status=open HTTP/1.1
Authorization: Bearer <accessToken>
```

```http
HTTP/1.1 200 OK
Content-Type: application/json
X-Total-Count: 137
X-Total-Pages: 7

[
  {
    "id": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
    "title": "Poutre fissurée hall B",
    "status": "open",
    "category": "neighborhood",
    "createdAt": "2026-07-08T09:12:00.000Z"
  }
]
```

### Robustesse des entrées

Deux garde-fous du contrat neutralisent les entrées malveillantes :

- **`search` échappé** — le terme est toujours interprété littéralement. Sur les stores PostgreSQL (incidents, utilisateurs) `escapeLike` échappe `%`, `_` et `\` avant le `ILIKE` ; sur les stores MongoDB (services, événements, quartiers, votes) `escapeRegex` échappe les métacaractères d'expression régulière avant le `$regex`. Aucune injection de motif `LIKE` ni de regex Mongo n'est donc possible.
- **`sort` en liste blanche** — `resolveSort` compare le champ demandé à la liste autorisée de l'endpoint et retombe sur `createdAt` si la valeur est inconnue ; une valeur `sort` forgée ne peut jamais atteindre la requête. `order` n'accepte que `asc`, toute autre valeur (ou son absence) donnant `desc`.

Les filtres MongoDB n'acceptent par ailleurs que des chaînes (`typeof … === "string"`), ce qui bloque l'injection d'opérateurs de type `?category[$ne]=`.

### Synchronisation delta (client bureautique)

- `GET /incidents?since=<ISO>` — synchronisation delta : ne renvoie que les incidents modifiés après l'horodatage ISO fourni (comparaison sur `updatedAt`). Utilisé par le pull incrémental du client bureautique JavaFX. Une valeur non parsable renvoie `400`. Ce paramètre s'ajoute aux paramètres communs sans altérer le format de réponse (toujours un tableau nu).

## Rôles et autorisations

La hiérarchie des rôles est `resident` → `moderator` → `admin`, à laquelle s'ajoute l'état `banned`. Les autorisations sont appliquées par les gardes `JwtAuthGuard` et `RolesGuard`, pilotées par le décorateur `@Roles` sur chaque route.

| Rôle / niveau | Périmètre |
|---------------|-----------|
| Public | Aucune authentification requise |
| Authentifié | Tout compte connecté (résident, modérateur ou administrateur) |
| moderator / admin | Modération : statut d'incident, suppression logique, exécution DSL |
| admin | Administration complète : utilisateurs, quartiers, statistiques |

Points saillants du modèle d'autorisation :

- **resident** — accès authentifié standard, cloisonné au quartier. Un résident voit les services de son quartier et les incidents de catégorie `neighborhood` de son quartier (même s'il n'en est pas l'auteur), plus **ses propres** signalements de modération (`reporting`, `bug`). Les signalements de modération d'autrui sont masqués de la liste, et `GET /incidents/:id` renvoie **404** (et non 403) sur un tel signalement, afin de ne jamais en révéler l'existence.
- **moderator** — mêmes limites de quartier qu'un résident (borné à son propre quartier), mais **toutes catégories d'incidents comprises**, plus la modération : `PATCH /incidents/:id/status`, `DELETE /incidents/:id` et l'exécution de requêtes `POST /dsl/query` (elles aussi scopées à son quartier).
- **admin** — périmètre global (liste l'ensemble des quartiers, services et incidents) et accès à l'administration : `GET /users`, `PATCH /users/:id/role`, gestion des quartiers, `GET /stats`.
- **banned** — état de compte bloquant. Le bannissement mémorise le rôle courant (`previousRole`) afin de le restaurer lors d'une réactivation.

> La colonne « Rôle requis » de la référence Scalar reflète les gardes réellement appliqués sur chaque route.

Les familles d'endpoints se répartissent selon la garde appliquée. Chaque niveau hérite des accès du niveau inférieur, suivant la hiérarchie `resident` → `moderator` → `admin` :

## Conventions

- **Identifiants** : PostgreSQL utilise des UUID, MongoDB des `ObjectId`.
- **Réponses d'erreur** : codes HTTP standards, complétés le cas échéant par un code applicatif dans le corps (par ex. `EMAIL_ALREADY_EXISTS`, `TOKEN_REVOKED`).

## Référence interactive Scalar

La spécification OpenAPI est générée à partir des décorateurs des contrôleurs (`@nestjs/swagger`) et exposée via une interface **Scalar** :

```
GET /docs
```

Le bundle Scalar est auto-hébergé (`/scalar/standalone.js`), sans dépendance à un CDN externe. L'interface permet de parcourir chaque route, d'inspecter les schémas de requête et de réponse, de renseigner un jeton via le bouton **Authorize**, puis d'exécuter les appels directement depuis le navigateur.
