---
title: Démarrage local
description: Prérequis, configuration et lancement en local
---

Ce guide décrit la mise en route d'une instance QuartierConnect complète sur un poste de développement. La plateforme s'exécute sous forme de **9 conteneurs Docker** orchestrés par Docker Compose : `caddy` (reverse proxy), `client` et `admin` (SPA React servies par Vite), `docs-user` et `docs-dev` (sites de documentation Fumadocs), `api` (NestJS + passerelle DSL Python PLY), et les trois bases `mongo`, `postgres`, `neo4j`.

## Prérequis

| Outil | Version / rôle |
|-------|----------------|
| Docker + Docker Compose v2 | Exécute toute la stack (`docker compose`) |
| Git | Récupération du dépôt |
| GNU Make | Orchestration des commandes (`make setup`, `make seed`…) |
| Node 22 + pnpm 9 | Exécution du seed sur l'hôte (`npx tsx`) |

> Les applications web, les sites de documentation et l'API tournent **dans les conteneurs** : Docker et Docker Compose v2 suffisent pour un lancement complet. Node et pnpm ne sont requis que pour exécuter des scripts hors conteneur (le seed notamment).

## Récupération du dépôt

```bash
git clone https://github.com/creibaud/QuartierConnect.git
cd QuartierConnect
```

## Configuration du fichier `.env`

Le plus simple est `make setup`, qui vérifie les prérequis, génère `.env` depuis `.env.example` avec des secrets aléatoires, démarre la stack et importe le jeu de démonstration — auquel cas les sections suivantes sont déjà couvertes.

Pour une configuration manuelle, copiez le template fourni **à la racine du dépôt** sous le nom `.env`, puis renseignez les secrets :

```bash
cp .env.example .env
chmod 600 .env
```

Générez chaque valeur avec `openssl rand -base64 24` (pas d'espaces ni de `<` `>` dans les mots de passe) et remplissez :

- `JWT_SECRET`
- `MONGO_ROOT_PASSWORD` — recopiez la **même** valeur dans `MONGO_URI`
- `POSTGRES_PASSWORD` — recopiez la **même** valeur dans `POSTGRES_URL`
- `NEO4J_AUTH=neo4j/<password>` — gardez `NEO4J_USER` / `NEO4J_PASSWORD` synchronisés

Vérifiez qu'aucun placeholder ne subsiste :

```bash
grep 'CHANGE_ME' .env && echo "⚠ Encore des placeholders" || echo "✓"
```

> Le mot de passe MongoDB n'est appliqué qu'à l'initialisation d'un volume vierge. Si vous le modifiez après un premier démarrage, MongoDB conservera l'ancien tant que le volume n'est pas recréé.

## Lancement de la stack Docker

En développement, on utilise uniquement `docker-compose.yml` (Caddy écoute en HTTP sur `:80`, sans TLS ni Let's Encrypt) :

```bash
make docker-up-build
# équivalent : docker compose -f docker/docker-compose.yml --env-file .env up -d --build
```

Cette commande construit et démarre les 9 conteneurs, **API, applications web et sites de documentation compris** — il n'y a pas d'étape de démarrage séparée. Vérifiez leur état :

```bash
make status
```

Caddy expose un point d'entrée unique et route en interne :

```
/          → client:3000
/admin     → admin:3001
/aide      → docs-user:3002
/dev       → docs-dev:3003   (basic auth)
/api       → api:5000
/api/docs  → api:5000/docs (Scalar, basic auth)
```

Les applications sont donc accessibles sur `http://localhost/` (résident), `http://localhost/admin` (back office), `http://localhost/aide` (aide utilisateur) et l'API sous `http://localhost/api`. Le site développeur (`/dev`) et la référence Scalar (`/api/docs`) sont protégés par une authentification basique Caddy : les identifiants proviennent des variables `DOCS_AUTH_USER` / `DOCS_AUTH_HASH` (une valeur par défaut de développement est fournie dans `docker/docker-compose.yml`).

## Seed des données de démo

Le seed s'exécute **sur l'hôte** (l'image API ne contient que le code compilé) : installez d'abord les dépendances de l'API, puis lancez le seed complet.

```bash
make install-api   # une seule fois (pnpm install dans api/)
make seed          # migrations Drizzle + comptes démo + graphe Neo4j
```

`make seed` enchaîne trois étapes : `db-migrate` (migrations Drizzle sur PostgreSQL), `seed-demo` (comptes alice/bob/admin via `npx tsx scripts/seed-demo.ts`) et `seed-neo4j` (peuplement du graphe depuis MongoDB).

> Si le migrator du bootstrap API rejoue la migration `0000` et plante, insérez une ligne de baseline dans `drizzle.__drizzle_migrations` (voir le RUNBOOK, section migrations).

## Vérification

L'API expose un point de santé agrégeant l'état des trois bases :

```bash
curl http://localhost/api/health
```

La réponse doit renvoyer `status:"ok"` avec `mongo`, `postgres` et `neo4j` remontés comme disponibles. Pour un contrôle de bout en bout (routes client/admin, `/api/docs`, WebSocket messagerie, en-têtes de sécurité), utilisez le script de smoke test :

```bash
./scripts/smoke-test.sh http://localhost
```

Une fois ces vérifications au vert, votre instance locale est opérationnelle : inscrivez un compte via `http://localhost/` ou connectez-vous avec un compte de démo issu du seed.
