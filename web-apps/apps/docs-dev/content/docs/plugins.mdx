## À quoi sert le système de plugins

Un plugin est un fichier JAR qui étend l'application desktop QuartierConnect sans en modifier le code source. Les plugins sont chargés au démarrage par `PluginRegistry` et peuvent apporter des tâches d'arrière-plan, des vues supplémentaires ou des intégrations avec des services externes.

Les plugins communiquent avec l'application en cours d'exécution exclusivement via l'interface `AppContext`. Ils n'ont **aucun accès direct** aux bases de données ni aux services internes.

## Interface de plugin

Tout plugin doit implémenter `fr.quartierconnect.desktopapp.plugin.QuartierConnectPlugin` :

```java
public interface QuartierConnectPlugin {
    String getId();       // Identifiant reverse-domain, ex. "fr.example.weather"
    String getName();     // Nom lisible affiché dans le gestionnaire de plugins
    String getVersion();  // Version semver, ex. "1.0.0"
    void onLoad();        // Appelé une fois après enregistrement — initialise les ressources
    void onUnload();      // Appelé une fois à l'arrêt — libère les ressources
    default String getDescription() { return ""; }
}
```

### Cycle de vie du plugin

`onLoad()` est appelé une seule fois à l'enregistrement (après l'injection éventuelle du contexte), `onUnload()` à l'arrêt. Le gestionnaire de plugins (`PluginsView`) ajoute un interrupteur par plugin : le désactiver rappelle `onUnload()`, le réactiver rappelle `onLoad()` — **sans jamais retirer le plugin du registre**. `unregister(id)` et `unregisterAll()` (au shutdown) appellent `onUnload()` puis ferment le `URLClassLoader` des plugins externes. Toute exception levée dans `onLoad`/`onUnload` est interceptée et journalisée ; le plugin reste enregistré et l'arrêt se poursuit.

## AppContext — ce à quoi les plugins accèdent

Le registre injecte un `AppContext` au chargement (via `setContext`), qui expose **exactement quatre getters — et rien d'autre**. C'est l'unique surface de contact entre un plugin et l'application en cours d'exécution :

| Getter | Type | Rôle |
|--------|------|------|
| `getScene()` | `Scene` | Scène JavaFX principale — injection de feuilles de style, extension de l'UI |
| `getIncidentRepository()` | `IncidentRepository` | Accès lecture/écriture au cache d'incidents SQLite local |
| `getToastManager()` | `ToastManager` | Affiche des notifications toast |
| `getEventBus()` | `PluginEventBus` | Publication/abonnement aux événements de l'application |

`AppContext` est une classe `final` immuable ; son constructeur prend exactement ces quatre dépendances :

```java
public AppContext(Scene scene, IncidentRepository incidentRepository,
                  ToastManager toastManager, PluginEventBus eventBus) { ... }
```

L'`AppContext` **n'expose ni `ApiService`, ni `AuthService`, ni `SyncService`**. Un plugin qui doit piloter le réseau passe par les points d'entrée statiques d'`ApiService` : `OfflineModePlugin`, par exemple, appelle `ApiService.setOfflineMode(...)` et `ApiService.isReachable()` directement.

Pour recevoir l'`AppContext`, implémentez `PluginRegistry.ContextAwarePlugin` en plus de `QuartierConnectPlugin` :

```java
public class WeatherPlugin implements QuartierConnectPlugin, PluginRegistry.ContextAwarePlugin {
    private AppContext context;

    @Override
    public void setContext(AppContext context) {
        this.context = context;
    }
    // ... autres méthodes de l'interface
}
```

Les plugins **ne doivent pas** accéder à `SQLiteDatabase` directement ; toute interaction avec l'UI passe par les points d'extension fournis ou par la `Scene`.

## Points d'extension de l'UI

Au-delà des services de l'`AppContext`, un plugin dispose de quatre leviers pour étendre l'interface, tous exacts au code :

| Levier | Accès | Consommateur | Exemple |
|--------|-------|--------------|---------|
| `incidentSlot` | `PluginRegistry.getIncidentSlot()` — `ObservableList<Node>` | `IncidentsView` (barre d'actions du tableau) | `ExportPlugin` y insère un bouton « Export CSV » |
| `topBarSlot` | `PluginRegistry.getTopBarSlot()` — `ObservableList<Node>` | `AppTopBar` | `OfflineModePlugin` y insère un interrupteur hors ligne |
| `ViewablePlugin.getPanel()` | interface optionnelle | `PluginsView` (modale « Configurer ») | `ThemePlugin`, `CompactModePlugin`, `NotificationPlugin` |
| Feuilles de style | `getScene().getStylesheets()` | scène JavaFX | `ThemePlugin` échange les thèmes, `CompactModePlugin` injecte un CSS data-URI |

Les slots sont des listes observables : le plugin ajoute son `Node` dans `onLoad()` et le retire dans `onUnload()`. La vue écoute la liste et se met à jour automatiquement — aucun couplage direct entre le plugin et la vue.

## EventBus — communication inter-plugins

`PluginEventBus` fournit un mécanisme publication/abonnement thread-safe (`CopyOnWriteArrayList`), évitant le polling. Les événements disponibles :

| Événement | Charge utile | Description |
|-----------|--------------|-------------|
| `INCIDENTS_CHANGED` | null | Les incidents locaux ont changé |
| `SYNC_STARTED` | null | Un cycle de synchronisation a commencé |
| `SYNC_COMPLETED` | null | Synchronisation terminée avec succès |
| `SYNC_FAILED` | String (message) | Échec de la synchronisation |
| `ONLINE_STATUS_CHANGED` | Boolean | La connectivité réseau a changé |

S'abonner et publier :

```java
context.getEventBus().subscribe(eventData -> {
    switch (eventData.event()) {
        case INCIDENTS_CHANGED -> context.getToastManager().show("Incidents updated");
        case ONLINE_STATUS_CHANGED -> updateStatusIndicator((Boolean) eventData.payload());
        default -> {}
    }
});

context.getEventBus().publish(PluginEventBus.Event.SYNC_FAILED, "Connection timeout");
```

> Les exceptions levées par un abonné sont interceptées et silencieusement ignorées — un écouteur défectueux ne casse ni les autres écouteurs ni le publieur.

## Écrire un plugin étape par étape

1. **Créer un module Maven** dépendant de `fr.quartierconnect:quartierconnect-desktop-api` en scope `provided`, packaging `jar`.
2. **Implémenter l'interface** `QuartierConnectPlugin` (et `ContextAwarePlugin` si l'`AppContext` est nécessaire).
3. **Déclarer l'implémentation via ServiceLoader** : créez le fichier `src/main/resources/META-INF/services/fr.quartierconnect.desktopapp.plugin.QuartierConnectPlugin` contenant le nom pleinement qualifié de la classe. C'est ainsi que `PluginRegistry.loadFromJar()` découvre le plugin à l'exécution.
4. **Empaqueter en fat JAR** :

```bash
./mvnw clean package -q
# Produit : target/qc-weather-plugin-1.0.0.jar
```

## Charger un plugin

**Depuis un JAR externe** — copiez le JAR dans le dossier `plugins/` (résolu relativement au répertoire de travail de l'application, via `Paths.get("plugins")`). Il est scanné au démarrage par `loadFromDirectory()`, et rechargeable à chaud depuis le gestionnaire de plugins (bouton « rescan », qui décharge les plugins externes puis rescanne le dossier) :

```bash
mkdir -p plugins/
cp target/qc-weather-plugin-1.0.0.jar plugins/
```

```java
AppContext ctx = new AppContext(stage.getScene(), new IncidentRepository(), toast, eventBus);
PluginRegistry.getInstance().loadFromDirectory(Paths.get("plugins"), ctx);
```

`loadFromDirectory()` liste les `.jar` du dossier par ordre alphabétique et délègue chacun à `loadFromJar()`, qui ouvre un `URLClassLoader` dédié puis découvre les implémentations via `ServiceLoader`. Un JAR sans entrée `META-INF/services` valide est journalisé (« No plugins found ») et son classloader refermé.

**Enregistrement programmatique (plugins internes)** — les six plugins intégrés sont enregistrés dans `MainView`, une fois la scène disponible (l'`AppContext` en dépend), avant le scan du dossier :

```java
PluginRegistry registry = PluginRegistry.getInstance();
registry.register(new ThemePlugin(), ctx);
registry.register(new CompactModePlugin(), ctx);
registry.register(new ExportPlugin(), ctx);
// ... NotificationPlugin, OfflineModePlugin, SpanishLanguagePackPlugin
```

Utilisez la surcharge sans contexte `register(plugin)` si le plugin n'implémente pas `ContextAwarePlugin`.

Les plugins internes partagent le classloader de l'application ; les plugins JAR reçoivent chacun leur propre `URLClassLoader` — c'est ce qui distingue un plugin « externe » d'un plugin « intégré » dans le gestionnaire.

## Contraintes

| Règle | Détail |
|-------|--------|
| Accès API uniquement | Passez par `ApiService` ; aucun appel direct JDBC/MongoDB/Neo4j |
| Pas d'accès au `Stage` | L'`AppContext` fournit la `Scene`, jamais le `Stage` ; injectez vos styles via `getScene().getStylesheets()` |
| `onUnload` propre | Annulez les tâches planifiées et fermez les connexions ; sinon avertissements et fuites de threads |
| Aucun stockage d'identifiants | Ne stockez ni tokens ni mots de passe sur le disque |
| Sûreté aux exceptions | Les exceptions de `onLoad`/`onUnload` sont interceptées et journalisées ; le plugin reste enregistré, l'arrêt se poursuit |
