Cette page décrit les mesures de sécurité implémentées côté API et client. Elle couvre le hachage des mots de passe, l'authentification multifacteur, les jetons JWT, les en-têtes HTTP, la limitation de débit et la conformité RGPD.

## Défense en profondeur

L'API n'oppose pas une seule barrière mais empile des couches indépendantes. Chaque requête traverse le proxy de bord, les middlewares HTTP, la chaîne de guards NestJS (`ThrottlerGuard` global puis `JwtAuthGuard` et `RolesGuard`), la validation des entrées, enfin la coercition des filtres avant d'atteindre la logique métier. Franchir une couche ne donne rien : il faut les passer toutes.

En production, **Caddy possède les en-têtes de bord** (CSP, HSTS, `X-Frame-Options`) : la configuration Helmet de l'API désactive donc ces mêmes en-têtes (`contentSecurityPolicy: false`, `strictTransportSecurity: false`…) pour ne pas les dupliquer, tout en conservant ses autres protections par défaut. Le `ValidationPipe` global est déclaré avec `whitelist: true`, ce qui **supprime silencieusement** toute propriété non déclarée dans le DTO — un attaquant ne peut pas glisser de champ inattendu dans le corps. Enfin, les valeurs issues du client qui servent de filtre MongoDB sont forcées en chaîne (`String(...)`) avant la requête, neutralisant l'injection d'opérateurs (`{ $ne: null }`, `{ $gt: "" }`…).

## Hachage des mots de passe — Argon2id

Les mots de passe sont hachés avec **Argon2id** (vainqueur de la Password Hashing Competition 2015), qui combine résistance aux GPU (coût mémoire) et résistance aux canaux auxiliaires. Les paramètres par défaut du paquet `argon2` sont utilisés :

- `type: argon2id`
- `memoryCost: 65536` (64 Mo)
- `timeCost: 3`
- `parallelism: 4`

L'inscription appelle `argon2.hash(dto.password)` ; la connexion vérifie via `argon2.verify(user.passwordHash, dto.password)`.

Le **jeton refresh JWT est lui aussi haché** en Argon2 avant stockage (`token.service.ts`). Un accès en lecture à la base ne suffit donc pas à rejouer un jeton refresh.

## Authentification multifacteur — TOTP RFC 6238

L'application impose un second facteur TOTP conforme à la RFC 6238 :

```
code = HOTP(secret, floor(Unix_timestamp / 30))
HOTP(K, C) = truncate(HMAC-SHA1(K, C_bytes))
```

Le code est valide 30 secondes avec une tolérance de ±1 période (`window: 1`). À l'inscription, `speakeasy.generateSecret` produit un secret base32 stocké en PostgreSQL, et une `otpauth_url` renvoyée au client pour générer un QR code.

La vérification intègre un **anti-rejeu en mémoire** : chaque couple `secret:token` accepté est mémorisé pendant 90 s (TanStack Store), et toute seconde présentation du même code est refusée. Même intercepté, un code valide ne peut donc pas être réutilisé.

## JWT — Access et refresh

Deux jetons HS256 sont émis :

| Jeton | Durée de vie | Stockage | Accès JS |
|-------|--------------|----------|----------|
| access | 15 minutes | `localStorage` | Oui — en-tête `Authorization: Bearer` |
| refresh | 7 jours | cookie httpOnly `qc_rt` (SameSite=strict) | Non |

Le payload contient `sub`, `email`, `role`, `jti`, `iat` et `exp`. Le jeton refresh, inaccessible au JavaScript (httpOnly), élimine le principal vecteur XSS ; en production le flag `secure` impose HTTPS. Le cookie `SameSite=strict` combiné à l'usage de l'en-tête `Authorization` pour l'access rend le CSRF impossible.

**Rotation stricte** — la rotation du refresh est protégée contre les conditions de course (TOCTOU) par un `SELECT FOR UPDATE` dans une transaction PostgreSQL. L'ancien hash est mis à `NULL` avant émission du nouveau : deux requêtes `POST /auth/refresh` simultanées ne peuvent pas réutiliser le même jeton, et le vol d'un refresh est détecté au prochain renouvellement légitime (révocation mutuelle).

Le schéma ci-dessous retrace le parcours complet, de la connexion à la rotation : vérification Argon2id du mot de passe, second facteur TOTP anti-rejeu, émission de la paire HS256, puis rotation du refresh sous verrou de ligne PostgreSQL.

La vérification du mot de passe et celle du TOTP sont **indistinctes du point de vue de l'erreur** : mot de passe ou compte inexistant renvoient le même `INVALID_PASSWORD`, ce qui évite d'indiquer à un attaquant quel facteur a échoué. Le rôle est relu depuis PostgreSQL à chaque rotation, si bien qu'un bannissement (`role = "banned"`) coupe l'accès dès le renouvellement suivant sans attendre l'expiration de l'access courant.

**Révocation instantanée** — à la déconnexion (`POST /auth/logout`), le jeton access courant est révoqué via son `jti` dans la table `revoked_tokens`, sans attendre son expiration. La stratégie JWT rejette tout jeton révoqué avec `{ code: "TOKEN_REVOKED" }`. Les entrées expirées sont purgées à chaque révocation, sans Redis ni tâche cron.

## En-têtes de sécurité HTTP

**Helmet.js** est appliqué à toutes les réponses, avec une CSP par route (Caddy + NestJS) :

| En-tête | Protection |
|---------|-----------|
| `Content-Security-Policy` | Restreint scripts/styles/images — mitigation XSS |
| `X-Content-Type-Options: nosniff` | Sniffing MIME |
| `X-Frame-Options: DENY` | Clickjacking |
| `Strict-Transport-Security` | Rétrogradation HTTPS → HTTP |
| `X-XSS-Protection: 1; mode=block` | XSS navigateurs legacy |

`'unsafe-inline'` a été retiré des routes client, admin et API ; seules les routes `/docs` et `/scalar` (UI Scalar tierce) le conservent dans `script-src`. Les applications React reposent sur des nonces implicites via Vite.

## Service des fichiers utilisateur

Les fichiers uploadés par les utilisateurs — pièces jointes de messagerie et avatars — sont stockés dans MongoDB GridFS puis servis par l'API. Le type MIME étant déclaré par le client à l'upload, il est traité comme **non fiable** au moment de servir le fichier :

- **Allowlist inline** — seule une liste blanche est servie avec `Content-Disposition: inline` : images matricielles (`png`, `jpeg`, `webp`, `gif`) et audios (`webm`, `ogg`, `mpeg`, `mp4`). Tout le reste — **HTML, SVG**, texte… — est forcé en `Content-Disposition: attachment` et servi en `application/octet-stream`. Un SVG envoyé en messagerie est d'ailleurs classé comme pièce jointe (`FILE`), jamais comme image inline.
- **Avatars** — toujours servis en `attachment`, et uniquement avec un type matriciel de la liste blanche (à défaut, `image/jpeg` est imposé).

Un fichier HTML ou SVG piégé ne peut donc plus être ouvert et exécuté dans le contexte de l'origine API : cette mesure neutralise le XSS stocké via les uploads.

## Limitation de débit

Un `ThrottlerGuard` global limite chaque IP à **100 requêtes / 15 minutes** (`ThrottlerModule.forRoot([{ ttl: 900000, limit: 100 }])`). Des routes sensibles ont des limites spécifiques :

| Route | Limite | Fenêtre | Raison |
|-------|--------|---------|--------|
| `POST /auth/login` | 5 tentatives | 15 min | Anti-force brute (TOTP + mot de passe) |
| `POST /auth/refresh` | 10 requêtes | 60 s | Limiter la rotation abusive |

## Autorisation basée sur les rôles

La hiérarchie est `resident → moderator → admin`, avec `banned` comme état terminal (401 à la connexion). Le `RolesGuard` **relit le rôle depuis la base** à chaque refresh — aucune confiance n'est accordée au seul JWT, si bien qu'un bannissement prend effet immédiatement. Au-delà des rôles, plusieurs contrôleurs appliquent un **cloisonnement par quartier** et un contrôle de propriété de la ressource (`createdBy === req.user.sub`).

### Confidentialité des incidents de modération

La visibilité des incidents ne se résume pas à un contrôle de propriété. Un résident voit **tous** les incidents de catégorie `neighborhood` de son quartier — même sans en être l'auteur — mais **ne voit pas** les signalements de modération (`reporting`, `bug`) d'autrui : ils sont filtrés de la liste. Surtout, `GET /incidents/:id` renvoie **404** (et non 403) sur un signalement étranger, afin de ne jamais révéler son existence. Un modérateur voit toutes les catégories, mais reste borné à son propre quartier ; seul l'admin est global.

### Périmètre et injection du DSL

Le DSL de modération (`POST /dsl/query`) est ouvert aux rôles `moderator` et `admin`, mais l'accès n'est pas global pour autant :

- **Scoping quartier** — tout appelant non-admin est borné à son `neighborhoodId` sur les collections `incidents`, `services`, `events` et `users` ; seule `neighborhoods` reste publique. Un modérateur sans quartier reçoit un résultat vide. Le DSL ne peut donc pas servir de porte dérobée pour lire d'autres quartiers.
- **Plafond de résultats** — toute requête `FIND` est plafonnée à **100 résultats**, avec ou sans `LIMIT` explicite.
- **`LIKE` échappé** — l'opérateur `LIKE` compile vers une recherche de **sous-chaîne littérale échappée** (la valeur passe par `re.escape`), et non vers un motif regex actif : les métacaractères sont traités littéralement, ce qui neutralise l'injection regex et le ReDoS.

### Anonymat des votes de communauté

Pour un vote marqué `isAnonymous`, l'API ne renvoie **jamais** les bulletins des autres votants : chaque réponse ne conserve que le bulletin de l'appelant (le client en dérive « a voté » et « mes choix »). Les totaux agrégés restent disponibles, sans aucun identifiant d'utilisateur. Un votant ne peut donc pas reconstituer qui a voté quoi.

## Contrôle de concurrence — soldes de points

Le transfert de points s'exécute dans une transaction PostgreSQL qui verrouille **les deux** lignes de solde (émetteur et destinataire) dans un ordre déterministe (tri par `user_id`, `SELECT … FOR UPDATE`). Cet ordre fixe élimine l'interblocage croisé de deux transferts A→B et B→A simultanés. Les erreurs Postgres résiduelles sont converties en réponses `400` exploitables plutôt qu'en `500` :

- `40P01` (deadlock détecté) → `{ code: "CONCURRENT_UPDATE" }`
- `23514` (contrainte `CHECK` de solde) → `{ code: "INSUFFICIENT_BALANCE" }`

## Cycle de vie d'un contrat — signature électronique

La signature électronique réutilise le second facteur de la connexion : signer un contrat exige un code TOTP valide (`totpService.verify`, même anti-rejeu qu'à l'authentification). Chaque signature est scellée par un **hachage SHA-256** de `contenu + userId + horodatage ISO`, poussé dans le tableau `signatures`. Le statut suit quatre états — `draft`, `partial`, `fully_signed`, `cancelled` — dont deux terminaux (`fully_signed` et `cancelled`).

<Mermaid
  chart={`stateDiagram-v2
  [*] --> draft
  draft: draft - contrat cree ou importe
  partial: partial - au moins un signataire a signe
  fully_signed: fully_signed - terminal, tous ont signe
  cancelled: cancelled - terminal, annule
  draft --> partial : 1re signature - claim atomique
  partial --> partial : signature suivante
  partial --> fully_signed : derniere signature
  draft --> cancelled : annulation
  partial --> cancelled : annulation
  fully_signed --> [*]
  cancelled --> [*]
  note right of fully_signed : reglement des points effectue AVANT ce passage
  note left of partial : reconciliation en lecture, flip si le paiement service est deja regle`}
/>

**Revendication atomique du créneau de signature** — la signature n'est pas un `read-modify-write` naïf. Elle passe par un `findOneAndUpdate` MongoDB dont le filtre revérifie atomiquement, dans la même opération, que le statut vaut `draft` ou `partial`, que l'appelant figure dans les `signatories` et qu'il n'a pas déjà signé (`"signatures.userId": { $ne: userId }`). Deux requêtes concurrentes du même signataire ne peuvent donc pas insérer deux signatures.

**Règlement des points AVANT `fully_signed`** — pour un contrat de service (présence d'un `bookingId`), le paiement en points (`completeServicePayment`) est réglé *avant* le basculement en `fully_signed`. Si le règlement échoue, la signature qui venait d'être poussée est retirée (`rollbackSignature`) et l'erreur remonte : un contrat de service ne peut jamais être `fully_signed` sans paiement effectif. Le basculement final est lui-même conditionnel (filtre `status: partial`) ; si une **réconciliation en lecture** (`findOne`, statuts *guérissables* `draft`/`partial`) l'a déjà basculé parce que le paiement était réglé, le résultat déjà `fully_signed` est conservé.

**Annulation défensive** — `cancelContract` bascule en `cancelled` via un `findOneAndUpdate` filtré par `status: { $nin: [fully_signed, cancelled] }`. Une annulation tardive ne peut donc jamais effacer un contrat déjà entièrement signé : sur un `fully_signed`, l'annulation est refusée par un `400`.

## RGPD — Protection des données

**Export des données personnelles** — `GET /me/export` renvoie une archive JSON complète (profil, incidents, services, événements, contrats, points, conversations). Elle n'inclut **jamais** `passwordHash`, `totpSecret` ni `refreshTokenHash`.

**Suppression de compte** — le processus enchaîne :

1. Soft delete des incidents (rétention pour modération)
2. Révocation du jeton refresh (déconnexion immédiate)
3. Suppression du nœud Neo4j via `deleteNode('User', id)`
